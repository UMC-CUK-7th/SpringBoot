- Spring Data JPA의 Paging
    
    DB마다 pagination을 위해 사용되는 쿼리는 다르다.
    
    **JPA**는 여러 DB 별 dialect를 추상화하여 하나의 방법으로 페이지네이션을 구현할 수 있도록 제공한다.
    전체 데이터 개수를 가져와서 전체 페이지 계산
    
    현재 페이지가 첫번째 페이지인지, 마지막 페이지인지도 계산
    
    예상치 못한 페이지 범위를 요청받았을 때 예외처리
    
    <br>
    
    **Spring Data JPA**는 이런 pagination도 추상화되어 있다. 각 페이지의 설정만 조정하여 전달하면 DB에서 해당 설정에 맞는 부분의 데이터만 조회할 수 있다.
    
    Spring Data JPA 레포지토리에 `Pageable` 을 전달하면, 반환 타입으로 위에서 나온 `Page` 와 `Slice`를 받을 수 있다. 두 인터페이스 모두 pagination을 통한 조회 결과를 저장하는 역할을 한다.

    <br>
    
    - Page
        
        `Slice` 를 상속받는다.
        
        `count` 쿼리를 실행하여, 전체 데이터 개수와 전체 페이지 개수를 계산할 수 있다.
        
        우리가 흔히 볼 수 있는 게시판의 pagination UI 등을 구현할 때 적합하다.

      <br>
        
    - Slice
        
        별도로 `count` 쿼리를 실행하지 않는다. 따라서 전체 페이지의 개수와 전체 엔티티의 개수를 알 수 없지만, 불필요한 count 쿼리로 인한 성능 낭비는 발생하지 않는다.
        
        infinite scroll과 같이 전체 페이지 개수가 굳이 필요하지 않는 상황에 자주 사용된다.

- 객체 그래프 탐색
    - 객체 A가 있을 때 A가 참조하는 다른 객체 B, C, D 등을 A를 통해 참조하는 것
    - 참조를 사용해서 연관관계를 탐색하는 것
    
    <br>
    
    SQL을 직접 다루면 SQL에 따라 객체 그래프를 어디까지 탐색할 수 있는지 정해진다.
    
    → DAO에 A를 조회하는 여러 메소드를 만들어야 한다.
    
    ---
    
    **JPA**를 이용하면 객체 그래프를 마음껏 탐색할 수 있다.
    
    JPA는 연관된 객체를 사용하는 시점에 적절한 SELECT SQL을 실행한다.
    
    → **지연 로딩**: 실제 객체를 사용하는 시점까지 데이터베이스 조회를 미룬다.
    
    A를 사용할 때마다 B를 함께 사용한다면 A를 조회하는 시점에 조인을 이용해서 B까지 함께 조회하는 것이 효과적이다. JPA는 연관된 객체를 즉시 함께 조회할지 아니면 실제 사용되는 시점에 지연해서 조회할지를 정의할 수 있다.
